# 로컬 BI Planner를 위한 데이터 설명서

이 문서는 기존 파일에서 확인한 사실과 업무적으로 미확인인 부분을 나눈 초안이다. 새 모델 다운로드나 BI 로그인·실조회 없이 작성했다. **현재 새 Planner는 독립된 fake 환경이며 우사기 실제 대화 경로는 아직 기존 Rasa를 사용한다.**

## 자료와 신뢰 범위

| 자료 | 확인한 내용 | 확정할 수 없는 내용 |
|---|---|---|
| `src/power-bi-model.json` | BO의 관측 열 127개, 측정값 참조 | 전체 스키마, 자료형, 관계, 원본 테이블 생성식 |
| `src/bi-reference/catalog.json`, `docs/power-bi/captures/queries/` | 성능 기록 6개에 포함된 42개 조회의 출력 식·필터·출처 | 참조 측정값 내부 DAX, 과거 필터의 현재 유효성 |
| `src/power-bi-visuals.json`, `src/power-bi-search.js` | 기존 상품 검색·표·시각화와 날짜 표현 방식 | 다른 화면에도 동일한 필터·단위가 적용되는지 |
| `src/commands/bi-metrics.js`, `bi-report-templates.js`, `bi-query.js` | 현재 실행하는 합산/원본/측정값/비중 구분 | 모든 업무 용어의 동치 관계 |
| `PERFORMANCE.md`, `DATA_CACHE.md` | 앱의 메모리·캐시 최적화와 별도 일정/실적 캐시 사용 | BI 모델의 테이블 생성 이력 |

이 범위의 작업공간에서 별도 SQL/TMDL/BIM/Power Query 테이블 생성 기록을 발견하지 못했다. 이를 분석 완료한 자료처럼 취급하지 않는다. 기존 API 설명 문서에는 초기 단계의 오래된 설명도 있어 현재 코드와 충돌하면 코드 및 원본 메타데이터를 우선한다. 캐시의 NAVI/Firebase 자료와 Power BI BO를 동일한 데이터셋으로 추정하지 않는다.

## 재생성 가능한 카탈로그

`npm run bi:catalog`가 다음 파일을 만든다.

- `data/bi-catalog.json`: 열 127개, 지표 153개, 차원 정의, 출처 파일 SHA-256, 과거 조회와 미확인 항목.
- `data/bi-tools.json`: 탐색 도구와 계획 Schema 위치. `data/`는 로컬 생성물이므로 Git에서 제외된다. 생성 코드는 `scripts/build-bi-catalog.js`에 보존한다.

원본 메타데이터·캡처·기존 계산식은 수정하지 않는다. 자료형이 없으면 `unknown`으로 표기한다. 방송일시의 datetime 분류는 기존 날짜 필터와 파싱 코드에 근거하며 서버의 정식 자료형 조회 결과는 아니다.

## 핵심 정의

- **브랜드 전체:** 편성코드의 맨 앞 `[브랜드]`가 정확히 일치하는 모든 상품. `[레이델]`에 `[레이델플러스]`를 포함하지 않는다. 별도 BO[브랜드]와 항상 같다고 추정하지 않는다.
- **조직:** 실제 조직 캐시에서 표준조직과 과거 조직명 별칭을 대조한다. 조직명 문자열을 마음대로 만들어 실행하지 않는다.
- **가중분:** 기존 코드는 BO[가중분]을 합산한다. 가중치 산정 방식과 원본 행의 중복 여부는 미확인이다.
- **편성비중:** 사용자 기본 기준은 가중분. 선택 조직의 합계 / 같은 기간·유/무형 조건의 전 조직 합계. 월별이면 분모도 각 월별이다. 원본 보고서의 추가 슬라이서가 있으면 비교 범위가 다를 수 있다.
- **방송횟수 비중:** 같은 조건에서 방송일시 고유 개수를 사용한다. 같은 시각은 1회이며 주문건수나 방송 상품 행 개수와 다르다.
- **마진/상품 수수료율:** 사용자 지정 BO[(전체/방송중)제휴포인트] 원본값. 임의 합계·평균·퍼센트 변환을 하지 않는다.
- **모델 측정값:** 확인된 참조로 호출하는 대상이며 내부 수식을 임의 재작성하지 않는다. Fake Executor는 수식을 모르면 명시적 오류를 반환한다.
- **취급고/취급액/주문금액:** 이름만으로 동일 지표로 확정하지 않는다. 취소·반품 반영 여부도 현재 자료만으로 확정하지 않는다.

## 계획 계약과 대화 동작

`src/planner/plan-schema.json`은 실행 가능한 계획, `turn-schema.json`은 모델이 반환하는 대화 동작과 patch의 JSON Schema다. 모델은 `new`, `add`, `modify`, `remove`, `confirm`, `cancel`, `clarify` 중 하나를 선택한다. 문장을 키워드로 재분류하는 코드는 이 계층에 없다.

- `new`: 이전 계획 대신 새 계획 생성.
- `modify`: 지정한 조건만 교체. 나머지 기간·대상·지표 유지.
- `add`: 배열 조건을 중복 없이 추가.
- `remove`: 지정한 계획 항목 또는 지정 필드의 필터 제거.
- `confirm`: 보관한 계획 확인. 미완성 계획은 Validator가 실행을 막는다.
- `clarify`: 질문을 반환하고 실행하지 않음. 원래 사용자 발화를 다음 턴에 함께 전달.
- `cancel`: 계획 삭제, 실행하지 않음.

시간은 한국 업무 시각, 날짜 범위는 시작 이상·끝 미만이다. 상대 날짜 해석은 오늘의 한국 날짜와 대화 문맥을 받은 모델의 역할이다. `8시`의 오전/오후가 불명확하면 모델이 확인 질문을 해야 한다. JSON 유효성 검증만으로 모델의 의미 해석이 옳음을 증명할 수는 없다.

## 도구와 역할 분리

| 파일 | 역할 |
|---|---|
| `src/planner/bi-tool-catalog.js` | listFields/searchMetrics/getMetricDefinition/searchTarget/getCapabilities. 로컬 자료만 탐색 |
| `src/planner/query-planner.js` | provider 주입, 최대 6단계 도구 탐색, 모델 출력 기록, 상태·검증·실행 조정 |
| `src/planner/dialogue-state.js` | 자연어를 읽지 않고 구조화된 patch를 적용 |
| `src/planner/query-validator.js` | Schema, 등록 열·지표·대상, 기간, 정렬, 조회량 검사 |
| `src/planner/fake-bi-executor.js` | 범용 filter/aggregate/groupBy/sort/listRows를 합성 행에 적용 |

실행기는 현재 `mode: fake`만 허용한다. Power BI bridge를 import하지 않으며 실제 DAX 생성·전송도 하지 않는다. 미등록 지표, 정의되지 않은 원본값 합산, 임의 실행 코드, 과도한 반환량을 거부한다. 대상은 검증된 로컬 엔티티 목록에서 확인한다. 이 검증은 실제 BI 권한 확인을 대체하지 않는다.

## 실행과 기록

```powershell
npm run bi:catalog
npm run planner:test
npm run planner:demo
```

데모는 날짜·시간 방송 목록, 브랜드 합산, 월별 수정, 지표 추가, 집계 제거, 취소를 보여준다. **질문을 이해하는 실제 모델이 아니라 미리 작성한 provider 응답을 사용한다.** 데모 성공은 도구·상태·검증·실행 연결을 확인한 것이며 LLM의 자연어 처리 성능이 아니다. 예시 숫자와 상품명은 합성 자료다.

`data/planner-demo-history.jsonl`에 대화/턴 연결, 사용자 원문, 이전 상태, 모델 출력 원문, 읽은 도구 자료, 최초 계획, Validator 결과, 검증된 최종 계획, 실행 여부·실행 모드·결과·오류를 남긴다. 확인 질문이나 검증 실패에는 `queryExecuted: false`다. 실행 중 오류가 나면 실행 시도는 true이고 error와 함께 기록한다. 기존 `conversation-history.jsonl`과 혼합하지 않아 가짜 결과가 실제 학습 데이터로 섞이지 않는다.

## 다음 연결 단계

1. 승인된 로컬 모델 실행기를 `provider.complete({messages, turnSchema, planSchema})` 계약으로 연결한다. 모델 공급자나 다운로드 방식을 이 기반 코드에서 강제하지 않는다.
2. 별도의 실제 사용자 질문 평가셋으로 의미 해석·도구 선택·후속 patch 정확도를 검증한다. 개발 중 작성한 scripted 계획은 모델 평가 정답 성공률로 사용하지 않는다.
3. 통과 후 검증된 계획만 받아 DAX를 만드는 실제 Executor와 연결한다. 모델의 임의 DAX를 실행하지 않는다.
4. 단계별 추적 기록을 실제 대화 기록과 연결한다. 사용자의 성공/실패 버튼을 요구하지 않고 수정·추가 발화와 앞뒤 계획을 보존한다. 이 기록이 자동 재학습이나 확정 정답이 되는 것은 아니다.
